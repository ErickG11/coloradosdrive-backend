## Antes de aplicar (requiere autorización del responsable de esa base)

### Contrato temporal del CRUD

POST `/practice-slots` y PATCH `/practice-slots/:id` aceptan `scheduledAt` con fecha
y hora de calendario ISO 8601 extendido y `Z` u offset explícito `±HH:mm`. Los segundos
son opcionales; su fracción, si existe, admite entre uno y seis decimales. Fechas solas,
horas sin zona, fechas u offsets inválidos y mayor precisión producen HTTP 400.
El mismo control se aplica a llamadas internas del servicio, antes de consultar Supabase.
El servicio normaliza a UTC conservando el instante y los microsegundos: por ejemplo,
`2026-03-01T08:00:00-05:00` y `2026-03-01T13:00:00Z` envían `2026-03-01T13:00:00.000Z`.
Omitir `scheduledAt` en PATCH conserva el inicio. El generador mantiene su conversión
explícita de horarios civiles de `America/Guayaquil` a UTC.

El formulario actual del frontend (`app/(admin)/admin/practice-slots/PracticeSlotForm.tsx`)
convierte `datetime-local` mediante `new Date(...).toISOString()` antes de POST y PATCH:
ya envía `Z` y no requiere adaptación para este contrato. Esa conversión usa la zona del
navegador, no una zona incorporada en `datetime-local`. Cualquier otro consumidor que
envíe valores sin zona debe definir el instante y enviar `Z` u offset antes de desplegar
este backend; no se interpreta silenciosamente como hora de Guayaquil.

## Qué falla y qué permanece

018 toma ACCESS EXCLUSIVE con lock_timeout de 5 s. La duración inválida o fecha no finita/
fuera de la representación del final produce `CD006`; los solapamientos producen `CD005`.
Se validan todas las duraciones, también las terminales. El lock evita nuevos datos entre
precondiciones y restricciones. La exclusión puede fallar igualmente si otra incompatibilidad
de esquema existe; cualquier error revierte la transacción completa de esa migración.
No hay UPDATE ni DELETE de registros. Falta de extensión/permisos/esquema aborta también.

019 verifica las tres restricciones de 018 y falla con CD007 si falta esa precondición.
018 y 019 son transacciones independientes. Si 019 falla, 018 permanece aplicada:
mantener la ventana y resolver el error o revertir 018 de forma coordinada. No lanzar
backend nuevo con funciones ausentes. El cron nuevo considera el reloj de PostgreSQL;
sus efectos externos siguen siendo best-effort, sin outbox ni garantía de entrega.

## Reversión

`cd-05-07-rollback.sql` admite dos estados de partida, que el responsable debe verificar
en la base elegida; este documento no acredita el estado de ningún entorno externo:

| Estado de partida | Procedimiento del mismo script |
|---|---|
| 018 y 019 completas y confirmadas | Elimina las funciones de 019 y luego revierte 018 |
| Solo 018 completa; 019 no aplicada o su transacción abortó | Omite las funciones ausentes de 019 mediante `DROP FUNCTION IF EXISTS` y revierte 018 |

Detener escritores y cron, mantener la ventana de mantenimiento y coordinar el retorno
al backend anterior antes de ejecutar manualmente el script completo con `ON_ERROR_STOP`.
Si el error de 019 dejó una transacción fallida en una sesión manual abierta, ejecutar
`ROLLBACK` en esa sesión antes de iniciar la recuperación. Con `psql` y `ON_ERROR_STOP`,
la salida de la sesión revierte una transacción que no llegó a confirmar. No intentar
continuar las sentencias de 019 tras un error ni reiniciar el backend nuevo sin sus RPC.

El rollback abre su propia transacción y adquiere ACCESS EXCLUSIVE con `lock_timeout`
de 5 s. Exige las tres restricciones validadas de 018 antes del DDL. No admite una 018
incompleta ni una reversión ya realizada; no es un script idempotente. Las firmas de
funciones están cualificadas y coinciden exactamente con 018/019, incluyendo el tipo
compuesto `public.practice_slots`. Primero elimina las tres RPC de 019, después
`practice_slot_transition_due` y luego `practice_slot_window_open`. Restaura los triggers
de rol y elimina `practice_free_instructors(timestamptz[], uuid)` de 018. No usa CASCADE:
una dependencia ajena produce error y aborta toda la transacción, incluso si un objeto
objetivo existe pero tiene dependientes inesperados.

Recrea el índice de inicios de 010 **antes** de eliminar la exclusión, retira las tres
restricciones de 018 y el default de duración y notifica la recarga del esquema PostgREST.
La exclusión vigente implica la unicidad anterior. Si falla el bloqueo, una dependencia,
el índice o cualquier sentencia, no se confirma una reversión parcial: mantener detenidos
los escritores, cerrar/revertir la transacción fallida y resolver la causa antes de
reintentar. Solo reanudar el backend anterior después de verificar el commit del rollback.
El script no ejecuta UPDATE/DELETE sobre filas ni elimina btree_gist u otras extensiones
compartidas. Registrar la reversión con el mecanismo operativo elegido para estos SQL;
el repositorio no incluye un runner/versionador de down migrations.

Se pierden la exclusión de intervalos (incluidos `liberado` y `completado`), la duración
obligatoria de 60 minutos y su default, la comprobación de inicio finito, la disponibilidad
por RPC y las acciones/transiciones atómicas con plazo y versión de fila. El índice
restaurado solo impide inicios iguales en `disponible`, `asignado` y `confirmado`;
el backend anterior vuelve a sus limitaciones de solapamientos y comprobaciones de plazo.

El runner existente prepara los dos escenarios en secuencia: revierte 018+019, reaplica
solo 018, revierte ese estado y reaplica 018→019. Compara el contenido completo de las
filas antes/después y comprueba la extensión y el índice anterior. **La ejecución real
de ambos rollbacks en PostgreSQL desechable se completó en el laboratorio documentado.** Leer el SQL, aprobar Jest
con mocks o comprobar la sintaxis JavaScript no demuestra una reversión exitosa.
